# 一场会议是怎样被处理的

这份说明写给第一次接触项目的人。它回答三个问题：为什么结果不会一次出现、不同模型分别做什么、
看到“待复核”或“处理中”时应该怎么办。实现细节再去看 `ARCHITECTURE.md`。

## 一分钟看懂

导入会议后，系统不是把整段视频直接交给一个大模型，而是分成几条可以核对的流水线：

1. **听清内容**：语音识别生成带时间码的原语言文字；命中已确认易误听词时，只复核对应短音频。
2. **分清是谁**：说话人分离、导入姓名和声纹绑定共同形成可导航身份。
3. **先给可读草稿**：视频仍在分析画面时，先用逐字稿快速生成语音草稿。
4. **理解共享画面**：把真正变化的页面分开，忽略参会人列表、鼠标和激光笔等小变化，再解释页面内容。
5. **生成正式纪要**：重新读取最新说话人身份，把逐字稿、页面资料和组织角色合并为纪要。
6. **核对有没有丢重点**：将正式纪要与早期草稿的重要决定、行动、风险和未决项按原始时间证据对照。
7. **形成会议脉络和检索资产**：生成时间线性的 Topic Map、证据链接和本地 RAG 索引。

逐字稿始终是“会上说了什么”的主证据；屏幕资料只能说明“当时展示了什么”。页面上出现一个数字，
并不等于会议已经批准它。组织职级只帮助理解谁有确认权限，也不能把一句建议自动升级成决定。

“说话人 K”表示本场尚未确认姓名的声音簇，不等于第 K 位真实人员。系统会跨会议匹配已经存在的声纹，
但同一场会议中新发现的两个匿名簇即使很相似，也先保持分开，避免把插话、远近变化或相似声线直接合成
一个人；用户确认属于同一人员后，才允许多条声纹归到同一个稳定人员身份。说话人修正不会改写 ASR 原文。

## 为什么使用不止一个模型

| 工作 | 当前模型角色 | 为什么这样分 |
|---|---|---|
| 视频会议早期语音草稿 | 35B MoE 快速模型 | 尽早让用户开始阅读，不等屏幕分析 |
| 纯音频正式纪要 | Qwen3.8-27B | 没有后续多模态终稿，需要一次生成正式结果 |
| 多模态正式纪要 | Qwen3.8-27B | 把质量预算放在最终摘要、待办、议题和分页讨论 |
| 共享画面理解 | 本地 VL 模型 | 读取表格、标题和图形，不负责宣布会议结论 |
| 会议脉络、翻译、AI 对话 | 现有 35B MoE | 保持交互速度，并避免每个操作都加载 dense 27B |
| 明确选择的高质量重跑 | 120B 量级 MoE | 慢且占内存，只在用户主动要求时使用 |

模型默认通过进程内本地适配器或本机回环服务调用。ASR 也支持显式配置兼容端点，但不会自行把音频
切换到远端；模型、硬件和供应商可以替换，上述角色与隐私边界应保留。

## 术语为什么不能只放一个大词表

语音识别开始前，系统会建立一次 ASR Context Pack。当前已上线版本包含：会议标题、人工确认术语，
以及至少在两场会议屏幕上重复出现的高置信候选。它只是帮助模型在声音相符时选择 `margin`、`EMEA`
等标准写法，不会在转写后做全文强制替换。

目前的限制是：可复用候选仍是全局池。随着术语变多，Portfolio/GEO 与 Business Mgmt/Finance 之间
可能互相带入无关提示，而且屏幕资料是在本场转写之后才沉淀，所以主要帮助下一场会议。

推荐的下一步分两层，避免为了少量错词重跑整场：

1. **主题选词（低成本，优先做）**：给术语增加领域标签；根据会议标题和已知系列选择相关词，仍受
   2400 字符上限约束。未命中领域时只使用人工确认的通用词。
2. **转写后术语复核（v1 已上线）**：第一遍完成后，只检查人工确认术语中明确记录的易误听写法，
   每场最多截取 12 个带少量前后语境的短音频重新识别。二次音频结果明确出现标准术语时才自动修正；
   否则只进入一个很小的“待核听”队列。不得让文本模型直接批量改写 canonical 逐字稿。

第二层不重跑整场，也不把文本流畅度冒充声学置信度。当前 v1 只处理“命中已确认混淆写法”，低置信
音频和本场屏幕上下文选词仍是后续能力。用户也可在工作台逐轮播放和修正原语言文本；系统保存快照，
并把纪要、脉络、翻译、证据和检索标记为待更新，避免旧结论继续伪装为最新。

## ASR Context 不兼容时会怎样

- 默认 `native` provider 在本机进程内运行；兼容 HTTP provider 只有管理员显式配置后才使用。
- `MEETING_ASR_CONTEXT_MODE=auto` 时，端点若明确拒绝 `prompt`，会在同一端点去掉 Context 重试；
  `required` 会直接失败，`off` 从一开始就不发送 Context。
- Context 和术语短片复核都属于增强层：复核失败保留第一遍逐字稿，不阻断后续流程。
- 说话人对齐需要字级时间戳。端点不能返回时间戳时明确报告能力不足；只有显式设置备用 provider
  才允许切换，绝不静默把内部音频发到别处。

## 用户会看到哪些状态

- **语音草稿可读**：可以阅读、播放和提问；屏幕内容仍在补充，暂不导出正式包。
- **可阅读**：正式纪要已生成，重要草稿事项都在终稿中找到对应证据投影。
- **终稿待复核**：正式纪要仍可读、可导出，但有重要草稿事项没有在终稿中匹配到。它可能被合并、
  被后文纠正，也可能真的遗漏；进入“结论审计”核对，不代表模型一定错了。
- **失败，可恢复**：根据保留的逐字稿、页面缓存等资产，只重跑需要的后半段；不会盲目重放旧命令。

## 哪些文件最重要

- `transcript.spk.json`：带说话人和稳定 T 编号的逐字稿真源。
- `transcript.review.json`：音频复核候选、自动/人工处理状态及其逐字稿 revision。
- `transcript.edits.json`、`.versions/`：人工文本修正记录和可撤销快照，仅留在私有会议目录。
- `minutes.md`：正式阅读纪要。
- `minutes.evidence.json`：纪要结论、待办与 T/P 证据的连接。
- `meeting.topic-map.json`：按时间组织的整场脉络。
- `slides.json`、`page_desc.json`：屏幕页面区间和画面解释。
- `meeting.generation.json`：只记录处理阶段与质量统计，不复制会议正文。

导出的 MeetingPack 把阅读需要的内容、证据和可选压缩媒体放进离线 Viewer；同事不需要安装模型。
