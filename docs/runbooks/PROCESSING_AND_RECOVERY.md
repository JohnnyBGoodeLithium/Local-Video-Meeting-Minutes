# 一场会议是怎样被处理的

这份说明写给第一次接触项目的人。产品的核心不是证明本地模型比云端更强，而是把散落的录音、
文稿、身份修正、屏幕资料和时间证据整理成可携带的会议上下文。它回答三个问题：输入怎样变成可信
资料、本地增强为什么可能分阶段出现，以及如何把结果交给同事、知识库或任意 AI。实现细节再去看
`ARCHITECTURE.md`。

## 一分钟看懂

系统优先复用用户已经拥有的高质量资料：Teams VTT/DOCX、其他云端转写或人工校对稿都可以直接
进入编译流程；只有资料缺失时，才调用本地 ASR、说话人分离和 VL 补齐。导入后不会把整段视频
直接交给一个大模型，而是分成几条可以核对、可以替换、可以降级的流水线：

入口先区分内容语义而不是复制管线：“会议”接收音频、录屏和 Teams 文稿；“媒体”接收单个本地视频或公开网页链接。公开链接先提取平台、发布者、标题、发布日期和时长，并将视频固化到本地；随后与本地媒体共用 ASR、说话人、镜头/VL、证据和导出能力，只在 prompt 与阅读投影上采用媒体语义。

1. **听清内容**：语音识别生成带时间码的原语言文字；命中已确认易误听词时，只复核对应短音频。
2. **分清是谁**：说话人分离、导入姓名和声纹绑定共同形成可导航身份。
3. **先给可读草稿**：视频仍在分析画面时，先用逐字稿快速生成语音草稿。
4. **理解共享画面**：把真正变化的页面分开，忽略参会人列表、鼠标和激光笔等小变化，再解释页面内容。
5. **生成正式纪要**：重新读取最新说话人身份，把逐字稿、页面资料和组织角色合并为纪要。
6. **核对有没有丢重点**：将正式纪要与早期草稿的重要决定、行动、风险和未决项按原始时间证据对照。
7. **形成脉络和检索资产**：生成时间线性的 Topic Map、证据链接和检索导出；媒体会进一步按口播、访谈或混合形态选择叙事/人物导航。

逐字稿始终是“会上说了什么”的主证据；屏幕资料只能说明“当时展示了什么”。页面上出现一个数字，
并不等于会议已经批准它。组织职级只帮助理解谁有确认权限，也不能把一句建议自动升级成决定。

“说话人 K”表示本场尚未确认姓名的声音簇，不等于第 K 位真实人员。系统会跨会议匹配已经存在的声纹，
但同一场会议中新发现的两个匿名簇即使很相似，也先保持分开，避免把插话、远近变化或相似声线直接合成
一个人；用户确认属于同一人员后，才允许多条声纹归到同一个稳定人员身份。说话人修正不会改写 ASR 原文。

## 为什么使用不止一个模型

| 工作 | 当前模型角色 | 为什么这样分 |
|---|---|---|
| 视频会议早期语音草稿 | 35B MoE 快速模型 | 尽早让用户开始阅读，不等屏幕分析 |
| 纯音频正式纪要 | Qwen3.8-27B | 没有后续多模态终稿，需要一次生成正式结果 |
| 多模态正式纪要 | Qwen3.8-27B | 把质量预算放在最终摘要、待办、议题和分页讨论 |
| 共享画面理解 | 轻量本地 VL；可选疑难页 27B VL | 全量页面优先速度，复杂表格/图表/OCR 页才升级复核；都不负责宣布会议结论 |
| 会议脉络、翻译、AI 对话 | 现有 35B MoE | 保持交互速度，并避免每个操作都加载 dense 27B |
| 明确选择的高质量重跑 | 120B 量级 MoE | 慢且占内存，只在用户主动要求时使用 |

模型默认通过进程内本地适配器或本机回环服务调用。ASR 也支持显式配置兼容端点，但不会自行把音频
切换到远端；模型、硬件和供应商可以替换，上述角色与隐私边界应保留。

媒体视频的画面理解可采用两级路由：主力 VL 先覆盖全部镜头，再从它的结构化结果中挑出证据帧里的
密集表格、复杂图表、跑分/规格页，以及明确报告“看不清、无法确认”的页面，最多复核管理员设定的
页数。口播、空镜和普通演示不会升级。复核模型逐页失败时保留主力结果，不让整个视频处理失败；两种
视觉模型顺序加载，结束后再生成文本纪要，避免同一时间常驻多份大模型。该增强默认关闭，只有同时配置
`MEETING_VL_REVIEW_MODEL` 与 `MEETING_VL_REVIEW_MMPROJ` 才启用，也可以替换为其他兼容 VL。
复核端点会校验实际加载的模型；若配置端口已被 embedding、reranker 等服务占用，会另选临时端口，
不会把“端口可访问”误当作“目标 VL 已就绪”。复核优先复用已生成的 `slides/full_*.jpg`，所以源视频按
存储策略清理后仍可继续；没有高分辨率帧时才尝试从仍存在的母版重抓，最终还可降级到分析截图。

## 术语为什么不能只放一个大词表

语音识别开始前，系统会建立一次 ASR Context Pack。当前已上线版本包含：会议标题、人工确认术语，
以及至少在两场会议屏幕上重复出现的高置信候选。它只是帮助模型在声音相符时选择 `margin`、`EMEA`
等标准写法，不会在转写后做全文强制替换。

目前的限制是：可复用候选仍是全局池。随着术语变多，Portfolio/GEO 与 Business Mgmt/Finance 之间
可能互相带入无关提示，而且屏幕资料是在本场转写之后才沉淀，所以主要帮助下一场会议。

推荐的下一步分两层，避免为了少量错词重跑整场：

1. **主题选词（低成本，优先做）**：给术语增加领域标签；根据会议标题和已知系列选择相关词，仍受
   2400 字符上限约束。未命中领域时只使用人工确认的通用词。
2. **转写后术语复核（v1 已上线）**：第一遍完成后，只检查人工确认术语中明确记录的易误听写法，
   每场最多截取 12 个带少量前后语境的短音频重新识别。二次音频结果明确出现标准术语时才自动修正；
   否则只进入一个很小的“待核听”队列。不得让文本模型直接批量改写 canonical 逐字稿。

第二层不重跑整场，也不把文本流畅度冒充声学置信度。当前 v1 只处理“命中已确认混淆写法”，低置信
音频和本场屏幕上下文选词仍是后续能力。用户也可在工作台逐轮播放和修正原语言文本；系统保存快照，
并把纪要、脉络、翻译、证据和检索标记为待更新，避免旧结论继续伪装为最新。

逐字稿完成若干处人工修正后，不必为了一个术语重新跑 ASR、说话人或 VL。工作台的“快速同步纪要”
只在 `page_desc.json` 已覆盖全部逻辑页时可用：它严格复用画面解读，更新 canonical 纪要与 evidence 后
立即让用户阅读；Topic Map、翻译和关键字继续按较低优先级排队。缓存缺页时快速路径会拒绝执行，并引导
用户使用标准重生成补齐资料；不会把缺失画面悄悄当成完整多模态结果。纯音频会议同样先更新纪要，再异步
更新脉络。检索索引仍按现有 revision 规则在下次使用时重建，不伪装成已经完成的后台阶段。

## ASR Context 不兼容时会怎样

- 默认 `native` provider 在本机进程内运行；兼容 HTTP provider 只有管理员显式配置后才使用。
- `MEETING_ASR_CONTEXT_MODE=auto` 时，端点若明确拒绝 `prompt`，会在同一端点去掉 Context 重试；
  `required` 会直接失败，`off` 从一开始就不发送 Context。
- Context 和术语短片复核都属于增强层：复核失败保留第一遍逐字稿，不阻断后续流程。
- 说话人对齐需要字级时间戳。端点不能返回时间戳时明确报告能力不足；只有显式设置备用 provider
  才允许切换，绝不静默把内部音频发到别处。

## 用户会看到哪些状态

- **处理中**：展示当前真实业务阶段、已完成单位和保守 ETA 范围；阶段不足以估算时不会伪造倒计时。
- **语音草稿可读**：可以阅读、播放、提问和导出核听快照；画面与正式纪要继续在后台补充。
- **可阅读**：正式纪要已生成，重要草稿事项都在终稿中找到对应证据投影。
- **终稿待复核**：正式纪要仍可读、可导出，但有重要草稿事项没有在终稿中匹配到。它可能被合并、
  被后文纠正，也可能真的遗漏；此时显示“核对关键结论”，不代表模型一定错了。
- **等待资源**：不是失败；已形成结果和检查点保留，资源恢复后有限次自动继续，等待期间 ETA 不递减。
- **降级完成**：主要结果可用，但明确标出缺少的非必要增强，例如剩余画面或语义检索。
- **失败，可恢复**：先说明失败步骤、原因、保留内容和阻塞范围，再预览将复用与重跑内容；默认从最近安全检查点继续，不盲目重放旧命令。

`job-progress/v2` 是刷新后仍存在的安全元数据，不保存会议正文、人名、标题、绝对路径、URL 或模型输出。新脚本通过受控 `[progress]`、`[phase_done]`、`[output_ready]`、`[failure]` 和 `[recovery]` JSON 事件更新它；普通日志不再被前端二次解析为正式状态。旧作业仍可读取，但会标记为历史估算。

当前实际阶段计划：Teams 文稿走“准备 → 对齐文稿与发言人 → 语音草稿 → 提取/理解画面 → 正式纪要 → 会议脉络”；无文稿视频走“准备 → 语音与发言人 → 语音草稿 → 提取/理解画面 → 正式纪要 → 脉络”；纯音频不显示画面步骤；公开视频链接前置下载；重新转写和重新生成只展示确实会重跑的后半段。本地 RAG/知识库不是这些主脚本每次都执行的固定尾阶段，因此没有发生时不显示。

## 哪些文件最重要

- `transcript.spk.json`：带说话人和稳定 T 编号的逐字稿真源。
- `transcript.review.json`：音频复核候选、自动/人工处理状态及其逐字稿 revision。
- `transcript.edits.json`、`.versions/`：人工文本修正记录和可撤销快照，仅留在私有会议目录。
- `minutes.md`：正式阅读纪要。
- `minutes.evidence.json`：纪要结论、待办与 T/P 证据的连接。
- `meeting.topic-map.json`：按时间组织的整场脉络。
- `slides.json`、`page_desc.json`：屏幕页面区间和画面解释。
- `meeting.generation.json`：只记录处理阶段与质量统计，不复制会议正文。

存量内容只需要因逐字稿时间切分、说话人修正或导出投影变化而重建纪要时，可使用
`minutes_by_page.py <目录> --reuse-vl-cache-only --skip-topic-map --publish`。该模式严格只读已有
`page_desc.json`，不会预启动、调用或回退到视觉模型；任一逻辑页缺少可读解读时直接失败，避免发布
伪完整结果。CLI 省略 `--skip-topic-map` 时仍同步更新脉络；Web 快速同步会先发布纪要，再排队更新脉络。

导出的 MeetingPack 把阅读需要的内容、证据和可选压缩媒体放进离线 Viewer；同事不需要安装模型。
如果接收者需要继续使用 GPT、豆包、Gemini、NotebookLM 或其他模型，选择“AI 上下文”导出：

- 单场生成一份 `.context.md`，可直接上传或粘贴；
- 多场生成一个 `.contextpack.zip`，入口为 `START_HERE.md`，包含索引、来源清单和逐场上下文；
- 不打包媒体、不依赖本机时间深链，并明确标注原始证据、屏幕资料与模型生成内容的边界；
- 文件仍可能包含内部信息，上传外部服务前必须按公司策略审阅或脱敏。

AI 上下文是当前最重要的机器消费出口。后续的历史会议 Lens、汇报演练或领导关注点分析属于接收模型
基于这些来源执行的下游任务，不在本应用内复制一套 NotebookLM。

如果目标是 WeKnora 等知识库，不要把 Viewer、JSON、媒体和多语言副本全部建索引：

- 只问文字内容、强调批量和体积：选“知识库轻量版”，解压后上传单份 `.kb.md`；
- 希望保留关键截图：选“知识库图文版”，直接上传单份 `.kb.html`；图片已以内嵌 JPEG 携带，不需要同时上传 `assets/`。会议侧已经生成画面文字解读，所以 WeKnora 的 VLM 默认关闭即可；只有要补读尚未文字化的表格字段、图表或演示细节时再开启。

两种 KB 文档中的时间码链接都负责从知识库答案回到本应用核听原声；这部分仍要求导出时填写接收者可访问的服务地址。HTML/Markdown 不含待转写音频，WeKnora 的 ASR 可以关闭。正在运行的多模态解析不会因修改知识库默认值自动回滚，应先取消该文档解析、关闭“多模态功能”，再重新解析。

配置知识库 API、key 和目标 allowlist 后，可从“更多 → 发布到知识库”直接发布。会议通常使用轻量文字，
媒体有关键画面或会议含现场照片时自动推荐图文；发布不调用 ASR/VL，也不等待知识库增强任务。未配置或
远端失败时仍可导出 KB 文档人工上传。若作业显示“等待计算资源”，
表示系统正在为 ASR、说话人或 VL 释放统一内存；逐字稿/页面缓存不会丢失，不要反复点击重跑。
完整部署、资源边界和移交清单见 `WEKNORA_INTEGRATION.md`。

现场照片是可选的会后补全阶段，不会阻塞 ASR、说话人、纪要或 VL。导入时固化原图并生成 JPEG 阅读副本；
EXIF 对得上会议时间才自动定位，否则由用户用当前播放位置校正或保持未定位。加入/调整照片后不重跑模型，
重新导出或重新发布知识库即可带上最新照片 revision。
