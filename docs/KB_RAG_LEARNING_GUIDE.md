# KB 与 RAG：结合本项目的学习与实验指南

更新时间：2026-08-28

这不是一份 API 手册，而是一份面向本项目的入门教材。读完后，你应该能够：

- 分清知识库、索引、检索、reranker 和生成模型各自负责什么；
- 看懂 Meeting Minutes → WeKnora 的数据流；
- 判断一个问题究竟出在源资料、分块、召回、排序，还是最终回答；
- 用一组固定问题做可重复的 KB/RAG 验收，而不是只凭“回答看起来不错”。

建议先用脱敏合成内容或自己明确选择的非敏感会议实验。不要把真实会议正文、凭据或人员信息复制到
Git、测试夹具和公开问题中。

## 1. 先用一分钟分清四层

```text
会议 / 媒体 canonical 数据
  逐字稿、身份、事实、纪要、画面、T/P/C 依据
                    │
                    ▼
知识投影（KB document）
  kb.md / kb.html：把一次内容整理成适合入库的一份文档
                    │
                    ▼
知识库（Knowledge Base）
  文档管理、权限、版本、分块、索引、保留与删除
                    │
                    ▼
RAG 检索
  词法召回 + 向量召回 → 融合 → reranker → 证据扩展
                    │
                    ▼
LLM 回答
  只根据选中的上下文组织答案，并给出引用/时间深链
```

四层的关键区别：

1. **canonical 数据**是可信源。说话人修正、逐字稿修正和结论审计应回到这里完成。
2. **知识投影**是为某种消费场景整理出的阅读副本，不是新的事实真源。
3. **知识库**解决“资料怎样保存、分块、索引、授权和更新”。
4. **RAG**解决“面对一个问题，先找到哪些资料，再让模型基于这些资料回答”。

因此，RAG 不是一个模型，也不是“把所有文档一次性塞给 LLM”。它是一条可诊断的检索与生成链路。

## 2. 最少但够用的术语

| 术语 | 在本项目中的直观含义 | 它不能保证什么 |
|---|---|---|
| Document | 一场会议或一个媒体内容的 `.kb.md` / `.kb.html` | 文档存在不代表能被正确检索 |
| Chunk | 知识库从文档切出的检索单元 | 越小或越多不一定越好 |
| Metadata | 日期、内容类型、来源、关键词、会议 ID、revision 等过滤字段 | 不是正文证据 |
| 词法检索 | 按人名、缩写、产品名、数字等字面匹配，类似 BM25 | 不擅长同义表达 |
| Embedding | 把问题与文本编码成向量，按语义相近程度召回 | 不判断事实真假，也不提供精确证据关系 |
| Hybrid retrieval | 同时使用词法与向量召回 | 仍可能召回太多相似但不相关的块 |
| RRF | Reciprocal Rank Fusion，把不同召回列表按排名融合 | 不能代替后续精排 |
| Reranker | 对“问题—候选块”重新评分，把更相关的块排前 | 相关不等于真实，不会修复错误源资料 |
| Evidence expansion | 命中结论后，按稳定 T/P ID 精确补回原话或画面 | 依赖上游已经建立正确 linkage |
| Context window | 最终交给 LLM 的问题与检索上下文总量 | 越大不一定越准确，噪声会稀释重点 |
| Grounded answer | 每个重要回答都能由给定来源支持 | 文风自然不等于 grounded |
| Revision | 一份知识投影正文的内容版本 | 产品版本号不能代替内容 revision |
| Idempotency | 同一 revision 重复发布不产生重复文档 | 不表示旧错误会自动修正 |

两个常用质量概念：

- **Recall（召回率）**：应该找到的依据有没有进入候选结果。
- **Precision（精确率）**：找到的候选中，有多少真的与问题相关。

RAG 常常先追求较高召回，再让 reranker 和上下文装配提高精确率。

## 3. 本项目中的对象怎样对应

| 层级 | 当前对象 | 用途 |
|---|---|---|
| canonical | `transcript.spk.json` | 原语言逐字稿、时间、说话人和身份 |
| canonical | `meeting.facts.json` | 比阅读纪要更完整的事实层 |
| canonical | `minutes.evidence.json` | claim、待办和 T/P/C linkage 真源 |
| derived | `meeting.topic-map.json` | 时间线性的会议/媒体脉络 |
| derived | `page_desc.json` | 共享画面或视频页面的标题、详情与价值判断 |
| KB projection | `profile=kb` | 单份轻量 Markdown，适合默认文字知识库 |
| KB projection | `profile=kb-html` | 单份自包含图文 HTML，保留筛选后的关键图片 |
| portable RAG source | `assets/rag/records.jsonl` | MeetingPack 中可移植的结构化检索原料 |
| local index | 私有会议目录 `.rag/` | 当前单场问答的向量和索引 manifest，不复制正文 |
| external KB | WeKnora knowledge base | 跨会议/媒体的分块、索引、ACL、问答和生命周期 |
| publication receipt | `meeting.knowledge-publications.json` | 只保存目标、远端文档 ID、profile、revision 和状态 |

`records.jsonl` 目前包含五类记录：

- `claim`：结论、共识、行动、风险，带 `evidence_ids`；
- `fact`：事实层中没有进入当前阅读纪要的事实，仍保留 T/P linkage；
- `transcript`：单轮原文及其时间、说话人、person 和页面；
- `slide`：画面理解、展示状态和相关讨论；
- `minutes_section`：适合宽泛主题检索的纪要章节。

这里最重要的设计不是“多存了几类文本”，而是**结论和原始依据之间有稳定 linkage**。向量检索只负责
找到候选；命中 claim 后，系统按 T/P ID 精确展开来源，而不是再用相似度猜一段原话。

## 4. KB 和 RAG 分别该做什么

### 4.1 知识库负责

- 一份文档属于哪个知识库、谁可以访问；
- 文档怎样分块、索引、更新、删除和保留；
- 跨会议、跨媒体或跨系列的检索范围；
- 文档解析状态、chunk 预览和索引健康；
- 可选的 Wiki、问题生成和图谱等增强。

### 4.2 RAG 负责

- 理解问题属于结论、待办、人物原话、画面还是宽泛主题；
- 从正确的内容范围中召回候选；
- 融合词法与向量结果并精排；
- 控制上下文的数量、类型和重复；
- 让生成模型只基于来源回答，并输出可回证引用。

### 4.3 不应让下游代替的工作

- WeKnora 不应重新决定谁在说话，也不应反写本项目的逐字稿和身份；
- 外部 VLM 不应默认覆盖会议侧已经生成的画面解释；
- reranker 不应把“材料展示”自动升级成“会议决定”；
- LLM 不应在没有来源时补负责人、期限或结论；
- 知识库中的手工改字不能代替 canonical 修正，否则下一次发布又会漂移。

## 5. 会议和媒体需要不同的知识形状

### 5.1 会议

用户通常问：

- 最终确认了什么？
- 谁负责什么，什么时候完成？
- 某个人具体说了什么？
- 这个数字来自发言还是 PPT？

所以会议默认强调：**结论、待办、人物、原话和可核听时间依据**。屏幕内容提供补充语境，但单独展示
一页 PPT 不能证明会议已经作出决定。现场照片同样只能补充白板/纸面信息，不能独立升级为决定证据。

### 5.2 媒体

用户通常问：

- 作者的核心论点和论证顺序是什么？
- 哪个片段展示了某项技术或图表？
- 这段内容来自哪个平台、发布者和原视频？

所以媒体默认强调：**叙事结构、论点、原文片段、关键画面和原视频来源**。除非内容明确布置行动，媒体
不应强行生成会议式负责人和待办。

这也是为什么两者共享音视频分析内核，但不应共用完全相同的 KB 文档模板。

## 6. 分块为什么会直接改变答案质量

假设一条行动项被切成两块：上一块只有“下周完成”，下一块只有“由 Alex 负责”。两块单独看都不完整，
检索即使命中其中一块，模型也可能漏掉负责人或期限。

### 6.1 块太小

- 语义被截断；
- 人名、动作、期限分离；
- 召回很多局部相似块，reranker 难以判断；
- 最终上下文充满碎片。

### 6.2 块太大

- 一个块混入多个议题；
- 关键词命中但真正答案只占很小部分；
- token 消耗和生成延迟上升；
- 引用只能指向大段文字，用户难以回证。

### 6.3 推荐的起点

- 先按文档语义结构切：摘要、结论、待办、每个议题、每页画面、逐字稿；
- 再对过长章节做带少量 overlap 的二次切分；
- 对需要上下文的短块保留 parent-child 关系；
- 人名、产品名、数字和时间等 metadata 可用于过滤或加权，但不要当作证据正文；
- 本项目已经提供画面的文字解释，因此 WeKnora VLM 默认关闭。只有验收目标包含“读取文字解释未覆盖的
  图片字段”时，再单独开启并做 A/B。

当前本地单场 RAG 会把过长 `minutes_section` 按约 1400 字符切分，步长约 1240，保留约 160 字符重叠。
这只是当前工程参数，不是所有内容类型的最佳答案。跨会议知识库应通过固定问题集实验，而不是盲目复制。

## 7. 一次检索到底发生了什么

以虚构问题“谁负责确认 Alpha 项目的报价，原话是什么？”为例：

1. **确定范围**：当前会议、某个系列，还是整个知识库；权限过滤必须在检索前生效。
2. **识别意图**：问题包含“谁负责”，优先 action/claim/fact；包含“原话”，也需要 transcript。
3. **多路召回**：
   - 词法检索容易命中 `Alpha`、`报价` 和姓名；
   - 向量检索可命中“核实价格”“确认商业条款”等同义表达。
4. **融合**：RRF 合并两路排名，避免某一路的分数尺度支配结果。
5. **精排**：reranker 比较问题与候选块，优先真正包含负责人和动作的记录。
6. **证据扩展**：如果命中 action claim，按其 T ID 精确补回原话和时间，而不是寻找另一段相似发言。
7. **生成**：LLM 组织一个简短答案，并把“已确认”“建议”“待确认”区分开。
8. **回证**：用户点击时间依据回到 Meeting Minutes 核听；发现错误时修正 canonical，再按新 revision 发布。

不同问题应优先命中不同记录：

| 问法 | 首选来源 | 还应补什么 |
|---|---|---|
| “最终决定了什么？” | `claim` / `fact` 的 decision、alignment | 对应 T/P evidence |
| “谁负责，期限是什么？” | 结构化 action | 负责人、状态、期限和原话 |
| “某人当时原话是什么？” | `transcript` | 相邻语境和时间 |
| “PPT 上的数字是多少？” | `slide` | 页面时间；标明是展示内容还是已讨论结论 |
| “这场内容主要讲什么？” | `minutes_section` / topic | 关键 claim 和代表性来源 |
| “作者怎样论证这个观点？” | 媒体 topic + transcript + slide | 原视频链接与片段时间 |

## 8. 先定位失败在哪一层

| 现象 | 常见根因 | 先检查什么 |
|---|---|---|
| 完全找不到正确依据 | 索引范围、分块、关键词/embedding、权限过滤 | 正确来源是否已入库；Recall@K |
| 正确依据在候选里但排名很低 | 融合权重、reranker、重复块竞争 | rerank 前后排名 |
| 召回正确但回答遗漏 | 上下文被截断、类型配额、生成提示 | 实际送给 LLM 的上下文 |
| 回答流畅但无依据 | 模型使用了先验知识或幻觉 | 每个事实是否有引用支持 |
| 引用存在但点开不对 | T/P linkage 或 `base_url` 错误 | 来源 ID、时间和深链地址 |
| 修正后仍回答旧内容 | 旧 revision 未替换、重复文档仍可检索 | 远端 document ID 与发布回执 |
| PPT 展示被说成决定 | source role 丢失或 prompt 过度推断 | `display_only` / discussion evidence |
| 同一答案出现互相冲突的版本 | 多份导出重复入库或版本未过滤 | meeting ID、revision、更新时间 |

在本项目调试单场问答时，优先调用只检索、不生成的：

```text
POST /api/meetings/{slug}/rag/search
```

它会报告 `hybrid_reranked`、`hybrid` 或 `lexical`。先确认检索是否拿到了正确来源，再调回答模型；否则
很容易把召回问题误诊为“小模型不会总结”。

## 9. 四个项目实验

所有实验都应使用同一份脱敏样本和同一组问题，改变一个变量后再比较。

### 实验 1：看懂一份知识文档

1. 选择一场非敏感测试会议，核听至少一个结论和一个待办。
2. 分别导出 `kb.md` 与 `kb.html`。
3. 检查是否只有一份主文档，而不是把 Viewer、JSON 和媒体重复上传。
4. 检查摘要、结论、待办、脉络、画面、逐字稿的结构和时间深链。
5. 在 WeKnora 中预览 chunk，记录一个完整行动项是否被切断。

### 实验 2：区分“召回失败”和“回答失败”

准备 10 个有人工预期来源的问题，至少覆盖结论、待办、原话、画面和宽泛主题。先用本项目的
`rag/search` 查看纯检索结果，再用助手生成答案。若依据没有进入 top K，先改检索；若依据已经进入但
答案错误，再检查上下文装配与生成。

### 实验 3：分块 A/B

在 WeKnora 中复制一个仅含脱敏样本的测试知识库，其他设置相同，只改变分块策略：

- A：默认自动分块；
- B：按标题/父子块，或调整目标块大小和 overlap。

比较固定问题集的 Recall@5、首个正确来源排名、引用可读性和延迟。不要同时打开 Wiki、问题生成和 VLM，
否则无法知道变化来自哪一个因素。

### 实验 4：验证 revision 与删除

1. 发布同一 revision 两次，应为 `already_current`，不能创建副本。
2. 在 canonical 中修正一处合成事实并重新导出。
3. 再次发布，应更新为新 revision。
4. 搜索旧表述，确认旧文档不再参与召回；搜索新表述，确认引用能回到正确来源。

## 10. 一张可长期维护的验收表

| Query | 预期 source type / ID | Top K 是否出现 | 首次正确排名 | 回答是否被来源支持 | 引用/深链正确 | 延迟 | 备注 |
|---|---|---:|---:|---:|---:|---:|---|
| 谁负责 Alpha 报价？ | action / C0001 → T0012 |  |  |  |  |  |  |
| 原话如何表达？ | transcript / T0012 |  |  |  |  |  |  |
| PPT 展示的目标是多少？ | slide / P0007 |  |  |  |  |  |  |

建议优先记录这些指标：

- **Recall@K**：人工标注的正确来源是否出现在前 K 条；
- **MRR**：第一个正确来源出现得有多靠前；
- **Citation precision**：引用中有多少真的支持对应陈述；
- **Groundedness**：答案中的重要事实是否都能由来源支持；
- **Deep-link accuracy**：时间链接是否到正确片段，而不是 00:00 或段落末尾；
- **Stale/duplicate rate**：修正后旧版本或重复文档是否仍参与召回；
- **Latency**：召回、rerank、首字和完整回答分别耗时多久。

不要把“回答写得像不像人”“内容够不够长”当作主要 RAG 指标。一个简短但可回证的答案，通常比一篇
流畅却混入模型常识的长回答更有价值。

## 11. 进阶研究：利益相关者审阅视角，而不是“人物模型”

Portfolio/PM 场景中，一个有价值但高风险的方向是：从多次会议中总结某位关键审阅者反复关注的问题，
帮助汇报者在正式会议前检查材料、模拟追问。这个方向可以做，但产品定义应是 **Stakeholder Review
Lens（利益相关者审阅视角）**，不是“复制一个领导”或推断人格。

### 11.1 可以提炼什么

- 明确表达过的决策标准，例如商业价值、成本、时间、风险或客户证据；
- 反复出现的关注主题和追问类型；
- 对数据粒度、对比口径、方案完整度和行动 owner 的要求；
- 在特定会议类型、业务阶段和议题范围内出现的审阅顺序；
- 已经发生变化或互相矛盾的偏好，以及它们各自的上下文。

不应提炼或宣称：性格诊断、隐藏动机、情绪倾向、政治立场、绩效判断，以及“此人一定会批准/拒绝”。
“经常追问成本”是可观察模式；“他只在乎成本”则是过度归因。

### 11.2 不要把幻觉永久写进 `领导.md`

推荐拆成两层：

```text
通用 rehearsal skill（可进代码库）
  规定如何取证、怎样表达不确定性、怎样生成检查清单和模拟问题
                         +
私有 stakeholder evidence store（不进 Git）
  observation + scope + meeting/turn/time evidence + confidence + 反例 + freshness
```

skill 本身不保存姓名、会议正文或人物结论。每次演练时，先根据当前汇报主题从私有 evidence store 召回
相关观察，再生成一个临时审阅视角。这样修正身份、删除会议或否定某条观察后，下一次演练可以立即变化，
不会把旧推断固化成永久 persona。

### 11.3 候选生成与人工确认

1. 只使用已经确认身份的本人发言；说话人仍不确定时不进入人物观察。
2. 模型只能提出 candidate observation，并附 meeting ID、T ID、时间、议题和原话链接。
3. 至少在多个独立场景中重复出现，才从“单次观察”提升为“暂定模式”；单场表述不能代表长期偏好。
4. 保存支持证据和反例，显示适用范围、最近出现时间与置信度。
5. 用户可确认、改写、驳回、设为过期；不能让模型自动把候选升级为事实。

第一版可以采用保守门槛：同一模式至少有 3 条跨会议证据，再允许进入默认演练视角；不足时仍可展示为
“本次会议观察”，但必须明确不代表稳定模式。门槛最终应通过样本验证调整，而不是作为心理学结论。

### 11.4 演练时应该输出什么

- “从此审阅视角看，当前材料还缺少哪些证据？”
- “可能被追问的 5 个问题”，每个问题附形成该判断的历史依据；
- 结论、数字、owner、期限和风险是否达到已观察到的审阅要求；
- 哪些问题只是低置信度假设，应由用户自行判断；
- 当前主题与历史证据不相似时，明确回答“资料不足”，而不是模仿口吻补全。

演练输出应使用中性的专业语言，不冒充本人、不生成带欺骗性的本人发言，也不把模拟问题写成“领导一定
会说”。其价值是扩大准备覆盖面，不是替用户作组织政治判断。

### 11.5 怎样证明它不是幻觉集合

可以做 leave-one-meeting-out 验证：用前 N-1 场已确认会议建立审阅视角，再检查它是否覆盖第 N 场中本人
真实提出的关注点。至少记录：

- 历史视角提出的问题中，多少真的在留出会议中出现（precision）；
- 留出会议中的重要关注点，有多少被历史视角覆盖（recall）；
- 每条建议是否能回到本人原话，而不是其他人的发言；
- 过期或换场景后，错误建议是否明显增加；
- 使用者是否因此发现材料缺口，而不是只觉得“模仿得像”。

如果这个实验不能优于一份通用的 PM/Portfolio 汇报检查表，就不值得建设人物层。先做一个私有、可审计
的单人 PoC，再决定是否产品化；涉及企业范围共享前，还必须确认组织的隐私、员工画像和访问控制政策。

## 12. 推荐学习顺序

### 第一阶段：先建立概念（约 30–45 分钟）

1. 读本文第 1、2、4、8 节。
2. 记住一条诊断原则：**先看检索结果，再看生成回答**。
3. 能口头解释“embedding 找相似，reranker 排相关，linkage 定证据”。

### 第二阶段：理解项目数据（约 1 小时）

1. 读 [处理流程](PROCESSING_GUIDE.md) 理解 canonical 与派生阶段。
2. 读 [导出与 RAG](EXPORT_AND_RAG.md) 第 4.3、5 节理解 KB Pack 和记录 schema。
3. 读 [WeKnora 集成](WEKNORA_INTEGRATION.md) 理解一键发布、revision、资源和职责边界。
4. 只在需要实现时再读 [系统架构](ARCHITECTURE.md)，不必一开始钻进 API。

### 第三阶段：做固定问题集（半天起）

完成第 9 节四个实验，保存脱敏问题、人工预期来源和指标。先建立 baseline，再讨论换 embedding、reranker、
分块算法或模型。

### 第四阶段：研究跨内容能力

当单场/单文档验收稳定后，再研究：

- 会议系列与媒体系列怎样分库、打标签和授权；
- query intent routing 是否应该区分结论、行动、人物、画面和叙事；
- meeting/media 是否需要不同的 chunk profile；
- evidence-aware reranking 能否优先可回证来源；
- 跨会议行动项如何表示状态变化，而不是把每次会议的旧待办都当成当前状态；
- 怎样从真实用户任务中形成脱敏评测集。

在这些 baseline 之前，不建议先投入 Graph RAG、自动知识图谱或大规模模板库。它们可能有价值，但会增加
新的解析和评测变量，不能替代基本的召回、引用和版本治理。

## 14. 最后记住的五句话

1. 知识库管理资料，RAG 为问题选择资料，LLM 组织答案。
2. embedding 给相似候选，reranker 调整相关性，二者都不证明事实。
3. 对会议而言，可回到原话/画面的稳定 evidence linkage 比“摘要更长”更重要。
4. 检索失败和生成失败必须分开诊断。
5. 没有固定问题、人工预期来源和 revision 治理，就没有可持续优化的 RAG。
